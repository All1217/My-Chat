## 市场主流 RAG 知识库隔离方案对比

### 核心问题回顾

多个知识库（如"考试学习"、"新闻分析"），用户只希望 AI 参考其中一个回答。市场上有几种主流做法：

---

### 方案一：Metadata 过滤（最主流，你的项目方案）

**代表产品：** Dify、FastGPT、MaxKB、Spring AI 官方推荐

**做法：** 所有文档的向量存储在**同一张表/同一个索引**中，每个 segment 的 metadata 里写入 `kb_id`，检索时通过 filter 表达式过滤。

```
向量表:
  id | embedding | text              | metadata
  ───┼───────────┼───────────────────┼────────────────────
  1  | [0.1,...] | "微积分定理..."   | {kb_id: "exam", ...}
  2  | [0.2,...] | "新闻快讯..."     | {kb_id: "news", ...}

检索:  similaritySearch(query).filter("kb_id == 'exam'").topK(5)
```

| 优点                        | 缺点                                           |
| --------------------------- | ---------------------------------------------- |
| 架构简单，单一数据源管理    | 知识库数量巨大时（1000+），filter 性能可能下降 |
| 跨知识库检索方便（OR 条件） | —                                              |
| 运维简单，一张表            | —                                              |
| pgvector 原生支持           | —                                              |

> **这就是你当前选择的方案，也是 Dify、FastGPT 的默认做法。**

---

### 方案二：多 Collection / 多索引（物理隔离）

**代表产品：** Pinecone（namespaces）、Weaviate（classes）、Elasticsearch（独立索引）

**做法：** 每个知识库创建独立的 collection/索引。

```
Collection "exam":    [向量] 微积分定理...
Collection "news":    [向量] 新闻快讯...

检索:  直接查询指定 collection，天然隔离
```

| 优点                            | 缺点                             |
| ------------------------------- | -------------------------------- |
| 完全物理隔离，不会相互干扰      | 知识库数量多时管理复杂           |
| 删除知识库只需 drop collection  | 跨知识库检索需要多个查询再合并   |
| 每个 KB 可设不同 embedding 维度 | pgvector 不原生支持多 collection |
| 性能不受其他 KB 数据量影响      | 运维成本高                       |

> Pinecone 的 namespace、Weaviate 的 class、Elasticsearch 的独立索引均采用此模式。

---

### 方案三：混合路由（Agent 自动选择知识库）

**代表产品：** LangChain（RouterChain）、Cohere RAG、自定义 Agent 方案

**做法：** 先用一个轻量级模型（或分类器）判断用户问题属于哪个知识库，再路由到对应库检索。

```
用户问 "微积分怎么求导"
       ↓
分类器/LLM 判断 → 属于 "考试学习" 库
       ↓
在 "考试学习" 库中检索 + 回答
```

| 优点                     | 缺点                           |
| ------------------------ | ------------------------------ |
| 用户无需手动选择知识库   | 分类可能出错，导致答非所问     |
| 体验好，一条输入框走天下 | 增加一次 LLM 调用开销          |
| 自动分流到不同 domain    | 冷启动问题，分类器需要训练数据 |

> Dify 的"知识库路由"功能、LangChain 的 RouterChain 采用此模式。

---

### 方案四：混合检索（向量 + 关键词）

**代表产品：** Elasticsearch（BM25 + 向量）、Weaviate（hybrid）、Milvus

**做法：** 同时做语义检索（向量相似度）和关键词检索（BM25/TF-IDF），结果融合后排序。

```
向量分:  "如何安装Python" → [0.1, 0.3, ...]  → 命中文档A(0.85)
关键词分: "安装" "Python" → 命中文档B(score 12.5)
融合:  RRF (Reciprocal Rank Fusion) 重排序
```

| 优点                           | 缺点                   |
| ------------------------------ | ---------------------- |
| 语义 + 关键词互补              | 实现复杂度高           |
| 专业术语（人名、编号）检索更准 | 需要额外的倒排索引     |
| Dify / FastGPT 专业版支持      | 对 pgvector 需额外部署 |

> **你的项目暂时不需要这个（pgvector 不支持原生 hybrid search），可以作为 P2 优化项。**

---

### 主流产品对比

| 产品               | 知识库隔离方式               | 用户选择方式                               | 检索增强            |
| ------------------ | ---------------------------- | ------------------------------------------ | ------------------- |
| **Dify**           | **Metadata 过滤**（方案一）  | 下拉选择知识库（手动）或路由 Agent（自动） | 向量 + 可选关键词   |
| **FastGPT**        | **Metadata 过滤**（方案一）  | 下拉选择知识库 + 数据集级别权限            | 纯向量，支持 rerank |
| **MaxKB**          | **Metadata 过滤**（方案一）  | 应用绑定知识库（每个应用指定一个）         | 向量 + 关键词       |
| **AnythingLLM**    | **独立工作区**（方案二变种） | 每个 workspace 隔离，切换工作区            | 纯向量              |
| **Pinecone**       | **Namespace**（方案二）      | 由调用方指定 namespace                     | 纯向量              |
| **腾讯云知识引擎** | **Metadata 过滤** + 资源隔离 | 应用级别指定知识库                         | 向量 + BM25         |

---

### 对你的建议

**当前选型（方案一：Metadata 过滤）是最佳选择**，原因：

1. **pgvector 完全支持** `filterExpression`，你们已经实现了
2. **Dify / FastGPT 都是这个路线**，经过市场验证
3. **架构简单**，不考虑跨知识库查询的场景下够用
4. **后续可演进**——如果需要自动路由（方案三），只需在 `RagChatController` 前面加一层分类判断，不改变底层存储

**下一步建议：**
- **先做用户手动选择**（下拉框选 KB），体验接近 Dify
- 根据用户反馈决定是否增加 **Agent 自动路由**（方案三）
- **暂时不碰 hybrid search**（方案四），pgvector 社区版不支持，需要额外引入 Elasticsearch
