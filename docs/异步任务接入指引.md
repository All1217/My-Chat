# 异步任务接入指引

慢活（向量化、批量导出、长时间计算）不要堵在 HTTP 请求里。业务接口只做「校验 + 落盘/记账」，然后丢给 `com.mychat.job` 后台跑。跑完后全局弹窗，用户人已经不在当前页也能收到。

现成例子：知识库上传 / 重新向量化 → `kb_ingest`（`KbIngestJobHandler` + `DocumentIngestService.submit(...)`）。

更细的设计背景见 [迭代规划/P2-11-异步任务+消息通知.md](./迭代规划/P2-11-异步任务+消息通知.md)。本文只讲「下次怎么接」。

---

## 先记住三句话

1. **没有「创建任务」的通用 HTTP 接口。** `JobController`（`/ai/jobs`）只负责查进行中的任务、挂 SSE。真正提交发生在业务 Service 里调用 `AsyncJobService.submit(...)`。
2. **每种任务类型要有一个 `JobHandler`。** `type()` 必须和 `submit` 时传入的 `jobType` 一模一样，否则任务会立刻 `FAILED`（原因：`未知 job_type`）。
3. **前端一般不用为新任务再接通知。** `App.vue` 已全局订阅 SSE；新类型结束时会自动弹窗。只有业务页要「完成后刷新列表」时，再听一下 `onJobTerminal`。

---

## 一条任务怎么跑起来

以「上传文档」为例（其它业务同理，只是换你自己的接口和 Handler）：

```text
浏览器 POST /ai/knowledge-base/documents/upload
        │  HTTP 立刻返回文档元数据（PROCESSING）
        ▼
DocumentIngestService.acceptOne
        │  文件落盘、写 document_meta
        │  asyncJobService.submit("kb_ingest", "向量化：xxx.pdf", docId, payloadJson)
        ▼
async_job 表插入一行（PENDING）
        │  dispatch(jobId)  ← @Async，换到 job 线程，HTTP 不等待
        ▼
AsyncJobDispatcher
        │  PENDING → RUNNING，SSE 推前端
        │  按 job_type 找到 KbIngestJobHandler
        │  handler.execute(job)
        │  SUCCEEDED 或 FAILED，再 SSE 推一次
        ▼
浏览器 notifyStore 弹窗 + 音效
```

你要接的新功能，走同一条路：**业务 API → `submit` → Handler**。不要去 `JobController` 里加 `POST /create`。

## 接入步骤

### 第 1 步：写一个 Handler

实现 `JobHandler`，做成 Spring `@Component`。启动时 Dispatcher 会把所有 Handler 按 `type()` 收进一张表，不用再改 Dispatcher。

骨架任务可以放在 `com.mychat.job`（和 `KbIngestJobHandler` 一起）。大厅功能包自己的任务，放 `com.mychat.apps.<id>` 也可以，只要是 `@Component` 且实现了接口。

```java
@Component
public class MarketSyncJobHandler implements JobHandler {

    @Override
    public String type() {
        return "market_sync";   // 必须和 submit 的 jobType 一致
    }

    @Override
    public void execute(AsyncJob job) throws Exception {
        // 从 job.getRefId() / job.getPayload() 取入参
        // 成功：正常 return
        // 失败：抛异常，调度器会写成 FAILED，并把 e.getMessage() 写入 error_message
    }
}
```

`kb_ingest` 目前只用 `refId`（文档 ID），`payload` 写了但 Handler 没读。新任务两种都能用：简单主键放 `refId`，多个字段放 `payload` JSON。

### 第 2 步：业务接口里 submit，不要同步干完

HTTP Controller 仍返回 `Result<T>`，里面调用业务 Service；Service 做完「必须同步」的事后调用：

```java
asyncJobService.submit(
        "market_sync",                 // jobType，对应 Handler.type()
        "同步行情：贵州茅台",           // title，用户弹窗上看见的那句
        watchId,                       // refId，业务主键，没有就传 null
        payloadJson                    // payload，Handler 入参 JSON，没有就传 null
);
```

四个参数里，**前两个必填**（空字符串会直接抛 `IllegalArgumentException`）。后两个可空。

对照仓库里的真实调用：

```java
// DocumentIngestService.acceptOne
asyncJobService.submit(JOB_TYPE, "向量化：" + filename, docId, payload);
```

前端打的是业务接口，例如：

- 上传：`POST /rag/ai/knowledge-base/documents/upload`
- 重新向量化：`POST /rag/ai/knowledge-base/documents/reindex`

上传接口返回文档列表，**不是**返回「等向量化结束」。通知靠全局 SSE。

### 第 3 步：前端（多数情况不用改）

页面加载时 `notifyStore.connect()` 已经：

1. `GET /rag/ai/jobs/active` 把刷新前还在跑的任务补回来
2. `EventSource('/rag/ai/jobs/events')` 听 `event: job`

新任务类型结束时，会按 `title`（成功）或 `errorMessage`（失败）弹 `ElNotification`。只有知识库那种「完成后要刷新表格」才需要：

```ts
notifyStore.onJobTerminal((job) => {
  if (job.jobType === 'market_sync') {
    reloadList()
  }
})
```

不要用 axios 订 `/ai/jobs/events`（拦截器当 `Result` 解包，而且 25 秒超时）。

## `submit` 四个参数：哪些能自由填

这是调用方**唯一能填**的入口。其它列由框架写，不要在业务里 `setStatus` / `setId`。

| 参数 | 对应表字段 | 必填 | 你怎么填 | 注意 |
| --- | --- | --- | --- | --- |
| `jobType` | `job_type` VARCHAR(64) | 是 | 自己起名，如 `kb_ingest`、`market_sync` | 必须已有 `JobHandler.type()` 与之相等；建议 snake_case |
| `title` | `title` VARCHAR(200) | 是 | 给用户看的短句 | 会出现在完成/失败弹窗；入库任务写成 `向量化：文件名.pdf` 这种 |
| `refId` | `ref_id` VARCHAR(64) | 否 | 业务主键，如文档 ID | 没有就 `null`。便于「同一文档是否已有进行中任务」这类查询 |
| `payload` | `payload` TEXT | 否 | Handler 用的 JSON 字符串 | 没有就 `null`。前端 **看不到** 这一列（SSE 的 `AsyncJobVO` 不含 payload） |

`title`、`jobType` 会 `trim()`；`refId` 空白会存成 `null`；`payload` 原样入库（不 trim）。

---

## 表上其它字段：不要当入参填

`async_job` 还有这些列，**submit 时不能指定**，由调度器 / 数据库维护：

| 字段 | 谁来写 | 含义 |
| --- | --- | --- |
| `id` | `submit` 生成 UUID | 主键 |
| `status` | 先 `PENDING`，再由 Dispatcher 改为 `RUNNING` → `SUCCEEDED` / `FAILED` | 只有这四个值 |
| `error_message` | Dispatcher 在失败时写入 | 来自异常 `getMessage()`，最长约 1000 字 |
| `created_at` / `updated_at` | MyBatis 自动填充 | 启动回收僵尸任务时会看 `updated_at` |
| `finished_at` | 进入成功或失败时写入 | 终态时间 |

状态机只能往前走：

```text
PENDING → RUNNING → SUCCEEDED
                  ↘ FAILED
```

终态不会再改。进程中途挂了，启动时 `StaleJobRecovery` 会把太久还停在 PENDING/RUNNING 的行标成 FAILED。

---

## 前端能看见的字段

SSE / `GET /ai/jobs/active` 推的是 `AsyncJobVO`：

`id`、`jobType`、`status`、`title`、`refId`、`errorMessage`、`createdAt`、`updatedAt`、`finishedAt`

没有 `payload`。不要把密钥、文件路径指望弹窗展示；路径类信息放 payload 给 Handler 用即可。

`kb_ingest` 在短时间内多条完成时，前端会合并成一条「入库完成 N 个」。其它 `jobType` 目前一条任务弹一次。

## 对照清单

- [ ] 有 `@Component` 的 `JobHandler`，`type()` 与 `submit` 的 `jobType` 一致
- [ ] 业务 Service 调用 `asyncJobService.submit(jobType, title, refId, payload)`，HTTP 不等待 Handler
- [ ] `title` 用户能看懂；`refId` / `payload` 按 Handler 需要填，没有就 `null`
- [ ] 没有去 `JobController` 加创建接口，也没有手改 `status`
- [ ] 失败靠抛异常，不要自己去 update 成 FAILED（除非你在写调度器）
- [ ] 前端通知已有全局订阅；只有要刷新本页数据时才 `onJobTerminal`

做完后：打你的业务接口应马上返回；过一会儿右上角弹出「任务完成」或「任务失败」。切到大厅/聊天，弹窗仍应出现。
