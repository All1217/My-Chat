# P2-10 进阶 3：可观测性（时间线）技术方案

> **依据**：[docs/迭代规划/P2-10-agents开发规划.md](../迭代规划/P2-10-agents开发规划.md) 「进阶 3：可观测性」  
> **参考**：  
> - [Spring AI — Recursive Advisors](https://docs.spring.io/spring-ai/reference/api/advisors-recursive.html)  
> - [Spring AI — ToolCallingAdvisor](https://docs.spring.io/spring-ai/reference/2.0-SNAPSHOT/api/tools/tool-calling-advisor.html)  
> - [spring-ai#6435 — 观测工具执行](https://github.com/spring-projects/spring-ai/issues/6435)  
> - [OpenCode 会话 / parts / SSE](https://github.com/anomalyco/opencode)  
> **目标**：主聊天能以时间线展示 AI 调用了哪些工具、参数与结果摘要（类 Cursor / OpenCode），并与 thinking / 最终回答分离。  
> **预估**：约 2～3 周（协议 → UI → 历史回放）

---

## 一、现状结论（为何现在「看不见 AI 干了什么」）

| 层 | 现状 | 后果 |
|----|------|------|
| 协议 | `ChatController` / `RagChatController` 返回 `Flux<String>`，`text/html`，仅文本 + 偶发 `[THINKING]…[/THINKING]` | 工具轮次若无文本，客户端像「卡住」 |
| 工具 | `toolChatClient` 内 Spring AI 自动 `ToolCallingAdvisor` 循环执行 `FileTools` / MCP | **从不写入 HTTP 流**；仅 `SimpleLoggerAdvisor` DEBUG 日志可见 |
| 前端 | `streamChat.ts` 整段拼接；`Message` 只有 `text` / `thinking` | 无步骤模型、无时间线组件 |
| 标签 | 后端 `[THINKING]`，前端找 `[THINKING_START]` | 思考折叠基本失效 |
| 记忆 | `spring_ai_chat_memory` 只存角色文本 | 刷新后工具轨迹丢失 |
| Agent | `POST /ai/agent/route` 同步返回 `{route,reasoning,answer}` | 未接入 ChatBox |

P2-10 原文建议：后端输出结构化事件（`step` / `tool_call` / `tool_result`）；前端时间线；与 thinking 标签分离——本方案将其落地为可执行设计。

```text
今天:  用户 → ChatController → Spring AI 工具循环 ──(不可见)──→ DEBUG 日志
                              └──────── 最终文本 ─────────────→ ChatBox 纯 Markdown

目标:  用户 → ChatController → ObservabilityAdvisor（旁路事件）──→ NDJSON 事件流 → 时间线 UI
                              └→ ToolCallingAdvisor 工具循环 ──→ 最终 text_delta → Markdown
```

---

## 二、对标 OpenCode / Cursor（学什么、不照搬什么）

OpenCode 核心模型（值得学）：

- **消息 = 有序 parts**：`text` / `reasoning` / `tool`（含 input、status、output）
- **实时**：SSE 事件总线（`message.part.updated` / `delta`）
- **持久化**：parts 入库，刷新可回放

My-Chat 约束更简单（单 POST 流式、FormData、无独立事件总线）。**采纳 parts + 事件流思路，不引入完整 OpenCode 会话运行时。**

| 决策点 | 本方案选定 |
|--------|------------|
| 传输 | **同一 POST 上的 NDJSON 行流**（继续 `fetch` + `ReadableStream`，不拆第二条 SSE） |
| 采集 | **自定义 `StreamAdvisor`**（order 落在 `ToolCallingAdvisor` 循环内侧）旁路发事件 |
| 注意 | Spring AI **2.0 GA 已删除** `streamToolCallResponses`；不可再依赖该 API |
| 主路径 | 先做 **普通聊天 `toolChatClient`**；RAG 第二期加 `retrieval`；Agent route 第三期 |
| 库表 | **第 1～2 周不改** `schema.sql`；第 3 周加轻量表做历史回放 |

## 三、目标协议（事件契约）

每行一个 JSON 对象。建议响应头：`Content-Type: application/x-ndjson;charset=utf-8`。

```json
{"v":1,"type":"thinking_delta","turnId":"...","seq":1,"text":"..."}
{"v":1,"type":"text_delta","turnId":"...","seq":2,"text":"..."}
{"v":1,"type":"tool_call","turnId":"...","seq":3,"id":"call_1","name":"ls","args":{"path":"."}}
{"v":1,"type":"tool_result","turnId":"...","seq":4,"id":"call_1","name":"ls","ok":true,"preview":"...","truncated":false}
{"v":1,"type":"error","turnId":"...","seq":5,"message":"..."}
{"v":1,"type":"done","turnId":"...","seq":6}
```

约定：

- `tool_call` / `tool_result` 用同一 `id` 配对（对齐 OpenCode tool part）
- `preview`：结果截断（建议 2～4KB），避免 MCP / 网页大 HTML 撑爆 UI
- `seq`：单调递增，前端乱序到达时可排序
- **禁止**再把事件塞进 Markdown 字符串里用标签混传
- 兼容：短期可用 query `?format=plain` 回退旧纯文本流；默认 NDJSON

前端内存模型（建议）：

```ts
type MessagePart =
  | { type: 'thinking'; text: string }
  | { type: 'text'; text: string }
  | {
      type: 'tool'
      id: string
      name: string
      args?: unknown
      status: 'running' | 'done' | 'error'
      resultPreview?: string
    }

interface Message {
  messageType: string
  text: string           // 最终文本（兼容复制 / 旧逻辑）
  thinking?: string | null
  parts?: MessagePart[]  // 时间线数据源
}
```

## 四、后端设计

### 4.1 事件旁路采集（关键）

新建例如：`my-chat-server/.../advisor/ObservabilityStreamAdvisor.java`

1. 实现 `StreamAdvisor`（必要时兼 `CallAdvisor`）
2. `getOrder()`：大于 `ToolCallingAdvisor.DEFAULT_ORDER`（官方示例量级：`HIGHEST_PRECEDENCE + 400`），进入工具循环内侧
3. `aroundStream`：`chain.nextStream(request).doOnNext(...)`
   - 见 `AssistantMessage.getToolCalls()` → 发 `tool_call`
   - 见后续请求中的 `ToolResponseMessage` → 发 `tool_result`（用 `Set` 去重 callId）
   - 文本 / `reasoningContent` 元数据 → `text_delta` / `thinking_delta`
4. 事件写入 **请求级** Reactor `Sink` / 队列，由 Controller 与主 `Flux` **merge** 成 NDJSON  
   - 旁路不得污染 `MessageChatMemoryAdvisor` 的对话历史（这正是官方删除 `streamToolCallResponses` 的原因）

控制器改造（`ChatController`）：

- 去掉「仅拼 `[THINKING]` + text」的单一映射
- `produces = "application/x-ndjson;charset=utf-8"`
- 结束时发 `done`；异常发 `error`；`doFinally` 清 `WorkspaceContext`

`FileTools` / MCP **不必改工具实现**；观测挂在 Advisor 层即可。  
可选：按 `name` 映射中文标题（`ls` →「列出目录」；MCP 搜索 →「网页搜索」）。

### 4.2 注册方式

在 `toolChatClient` 的请求级 `.advisors(...)` 注入带 `Sink` 的观测 Advisor（**Sink 必须是请求级**，禁止单例共享状态）。

实现时关键注释建议标明：

```text
// 代码路径：Advisor 旁路采集 → Controller merge 成 NDJSON
// 单次 LLM / 工具：仍由 ToolCallingAdvisor 自动循环，模型决定调哪个工具
```

### 4.3 RAG / Agent（分期）

| 阶段 | 内容 |
|------|------|
| A | 普通聊天工具时间线（本进阶主目标） |
| B | RAG：`retrieval` 事件（topK 片段 id / 标题，勿倾倒全文） |
| C | `/ai/agent/route`：增加 `steps[]` 或改为可流式；ChatBox 可选调试入口 |

### 4.4 安全与体量

- 截断大 `tool_result`；可选脱敏绝对路径
- 不把 API Key / 环境变量打进事件
- 超时继续依赖现有 `read-timeout`

## 五、前端设计

### 5.1 流解析

改造 `my-chat-vue3/src/utils/streamChat.ts`：

- 行缓冲：按 `\n` 拆 NDJSON，`JSON.parse` 后 `onEvent(event)`
- 回调从 `onMessage(chunk)` 升级为 `onEvent`（可保留兼容包装）

改造 `composables/useChatStream.ts`：

- 维护进行中的 `parts[]` + 最终 `text`
- `tool_call` → 插入 `status: 'running'`；`tool_result` → 更新同 `id`

### 5.2 时间线 UI

新建例如 `components/AgentActivityTimeline.vue`，挂在 `ChatBox.vue` 助手气泡内：

- Element Plus `el-timeline` 或自定义竖线列表（贴合现有 Less）
- 每项：图标 + 工具名（中文映射）+ 可选耗时 + 折叠的 args / result
- 流式中：running 显示 loading；完成后默认可折叠
- thinking：独立折叠块（消费 `thinking_delta`），**删除**错误的 `THINKING_START` 解析

视觉参考：OpenCode / Cursor 的「可展开 tool 行」，保持 My-Chat 现有气泡风格，**不做**完整 IDE 侧栏。

### 5.3 历史加载

- 第 1～2 周：刷新后仅最终文本（与今天一致）
- 第 3 周：历史 API 带回 `parts`，时间线可回放

## 六、数据库（第 3 周）

`my-chat-server/src/main/resources/schema.sql`：**第 1～2 周不动**。

第 3 周在 **PostgreSQL 段**新增：

```sql
CREATE TABLE IF NOT EXISTS chat_turn_events (
  id              BIGSERIAL PRIMARY KEY,
  conversation_id VARCHAR(64) NOT NULL,
  turn_id         VARCHAR(64) NOT NULL,
  seq             INT NOT NULL,
  event_type      VARCHAR(32) NOT NULL,
  payload         JSONB NOT NULL,
  created_at      TIMESTAMP DEFAULT CURRENT_TIMESTAMP
);

CREATE INDEX IF NOT EXISTS idx_turn_events_conv
  ON chat_turn_events (conversation_id, turn_id, seq);

COMMENT ON TABLE chat_turn_events IS '单轮对话可观测事件（工具调用/检索等），用于前端时间线回放';
```

约定：

- 流结束时批量写入本轮事件（或只存 `tool_*` + 最终 text 摘要）
- `GET /ai/history/getMessages/{id}` 扩展返回 `parts`，或新增 `GET .../events?conversationId=`
- **不**改写 `spring_ai_chat_memory` 结构，避免干扰 Spring AI JDBC Memory

## 十、风险与缓解

| 风险 | 缓解 |
|------|------|
| Advisor order 不对，采不到 tool 帧 | 对照 Recursive Advisors；DEBUG 日志断言每轮 `hasToolCalls` |
| merge Flux 乱序 | 事件带单调 `seq`；前端按 seq 排序 |
| DeepSeek / 工具结果非结构化 | `tool_result.preview` 当纯文本 |
| 大结果卡顿 | 截断 + 折叠默认收起 |
| 与 Memory Advisor 冲突 | 事件只走旁路 Sink，不把未配对 tool 帧写回主对话流 |

---

## 十一、初学者建议路径

1. 精读 Spring AI **Recursive Advisors**，确认「观测 Advisor 在 ToolCallingAdvisor 内侧」
2. 本地开 `logging.level.org.springframework.ai=DEBUG`，先看清工具循环，再写 Advisor
3. 第 1 周只用 curl / IDEA HTTP 看 NDJSON 行，**先别做漂亮 UI**
4. 第 2 周再做时间线；对照 OpenCode 的 part 模型，但保持实现最小
