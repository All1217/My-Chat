# 主聊天后端架构（通俗版）

不必会写 Java，也可以把主聊天想成两层：**外面是一条流水线，里面是一个领班带几个工人。**

用户发一句话 → 后端按固定工序走完这一回合 → 边走边把进度推到聊天窗口（一行行 NDJSON）。工序写死在代码里，所以「再加一段业务」通常是**流水线上加一站**，不是把所有逻辑再塞进一个大文件。

```text
你在网页里点发送
        ↓
门口接待（ChatController）
  检查格式、绑工作区、处理附件
        ↓
前台（ChatOrchestrateStreamService）
  只负责把客人交给流水线，自己不干活
        ↓
流水线（ChatTurnPipeline）按站走完
        ↓
收尾处（ChatTurnFinalizer）按「成功 / 取消 / 出错」记账
```

## 外层：流水线（一回合怎么走完）

像工厂里的传送带：**每一站只做一件事，做完交给下一站。** 现在固定五站，顺序不能乱：

| 站名 | 人话 | 代码里叫 |
|------|------|----------|
| 1. 亮灯 | 先告诉前端：本回合走「多步编排」，时间线出现一条 route | `emit_route` |
| 2. 翻旧账 | 把最近几轮对话（太长的压成摘要）递给后面，让模型记得「刚才说的那个」 | `load_dialogue` |
| 3. 干活 | 领班决定用知识库 / 文件 / 搜索 / 闲聊，工人做完汇报 | `orchestrate` |
| 4. 写给用户看 | 把材料润色成最终答复，一个字一个字流到气泡里 | `stream_final` |
| 5. 质检（可选） | 如果刚才真的往磁盘写了文件，再派人检查写得对不对；没写文件就跳过 | `quality_loop` |

这就是常说的 **Pipeline（管道 / 流水线）**。它和「责任链」有点像，但责任链是「谁能处理谁截住」；这里是**能跑的站都按序跑一遍**，某一站内部可以自己跳过（比如没写文件就不质检）。

以后要加「自动起个会话标题」「回答前过一遍安全检查」，正确做法是：**新建一站，插进这张表的某一行**。不要把 Memory、`done`、时间线落库做成普通一站——那三件事看的是「这一回合到底是成功结束、用户划走、还是中途报错」，必须放在流水线外面的收尾处，否则取消时会记错账。

## 内层：领班 + 工人（一步怎么选能力）

流水线第 3 站里，不是一个全能机器人什么都干，而是：

1. **领班**（编排器）看目标和已经做完的事，喊一句：下一步去查库 / 动文件 / 上网 / 自己想想 / 可以收工了。
2. **对口工人**去干：知识库工人、文件工人、搜索工人、闲聊工人。
3. 工人把「看到了什么」交回领班。简单任务干完一站就收工；复杂任务最多再转几圈（有上限，防止死循环）。

工人各管一摊，换人或加一种能力，主要改「领班点谁、谁来干活」，不必重铺整条传送带。这就是 **Orchestrator-Workers（编排器–工人）**；工人这一层也常叫 **Strategy（策略：同一种「去干活」，换一套做法）**。

领班每做完一步，会按一下铃通知流水线，前端时间线就多一条 step。这只是「做完叫一声」，不是满屋子广播的事件总线。

## 收尾处：和流水线分开

传送带转完（或客人中途离开），**收尾处**才记账：

- 成功走完：把短问答写入对话记忆，并给前端发一个 `done`。
- 无论成功、取消还是出错：只要有过程轨迹，就异步存进时间线表，刷新页面还能回放。

记忆里只放「文件名 + 原问题」这种短用户话，附件全文只给本轮工人看，避免历史被一篇 PDF 撑爆。工人干活时用临时工号（`orch-*`），不会把中间草稿写进你的会话记忆。

## 一张对照图

```text
网页发消息
  → 门口接待
  → 前台（门面，不办事）
  → 流水线五站
        → 第 3 站：领班循环点将
              → 知识库 / 文件 / 搜索 / 闲聊 四个工人
  → 收尾处按信号记账
```

| 你听到的术语 | 在本项目里是什么 | 用来解决什么 |
|--------------|------------------|--------------|
| Pipeline | 外层五站传送带 | 回合前后加长流程 |
| Orchestrator-Workers | 第 3 站里的领班 + 工人 | 一句话里换几种能力 |
| Strategy | 四个工人各一种干法 | 加新能力不拆整条带 |
| Facade | 前台那个薄服务 | Controller 不用认识流水线内部 |
| 回调 | 领班做完一步按铃 | 时间线能实时画 step |

后台「入库任务」那套（`JobHandler`）是**按任务类型选一个执行器**，和主聊天不同：主聊天要的是**有顺序的多站**，所以做成流水线，而不是再做一个任务分发器。

# Orchestrate 长对话上下文（滚动摘要 + 近期原文）

主聊天编排**不**给 Worker 挂 `MessageChatMemoryAdvisor(chatId)`（避免与 `orch-*` 临时会话双写）。读路径由 `OrchestrateDialogueContextService` 拼上下文注入 decideNext / Worker / 最终流式：

1. **近期原文窗口**：最近约 10 条 USER/ASSISTANT（单条约 800 字、合计约 4000 字）。
2. **滚动摘要**：旧消息攒够约 6 条时，用无工具 Client 压成中文摘要写入 `chat_session_summary`（按 `covered_until_sequence_id` 增量覆盖）；再与近期原文一起注入。
3. **写路径不变**：回合末仍手动 persist 短 USER + 最终 ASSISTANT；摘要只在读路径惰性更新。

实测：Memory ≤10 条时摘要表可为空（全在窗口内）；超过窗口后会 `INSERT` 并出现非空「会话摘要」段。摘要调用会拖长该轮首包延迟，属有损压缩。

该链路嵌入主线程，没有异步，会影响性能。

# 特殊技术栈

`Project Reactor`：[Project Reactor](https://projectreactor.io/)

## 模型总览

传统同步阻塞：调一个方法，线程卡住等返回。该库采用`发布者-订阅者`模型：

1. 你先描述一条管道：数据从哪来、怎么变、往哪送（`map` / `flatMap` / `doOnNext`…）。
2. 有人订阅之后，管道才真正开始跑。
3. 上游推数据，下游收；下游忙不过来时可以要慢一点（背压），避免被冲垮。

`Mono` / `Flux` 就是这条管道上的两种「发布者」：一个最多一件货，一个可以一串货。

**Flux：多元素发布者**

像**水管**：可以陆续流出 0～很多个值。

主聊天返回 `Flux<String>`：每一行 NDJSON（`route`、`step`、`text_delta`…）就是管子里冒出来的一滴水，前端边收边画。

**Mono：单元素发布者**

像**快递单**：要么送来一件货，要么空着/出错，**不会**连送一串。

例如 `streamFinalAnswer` 整段跑完用 `Mono<Void>` 表示「这件事做完了」；`orchestrate` 包进 `Mono.fromCallable(...)` 表示「异步算出一份编排结果」。

**Sinks：发布者与订阅者之间的管道**

总体来说是管道，但不是纯粹的无状态管道，还携带了消息上限限制。

**背压**

本质是订阅者向发布者的一种反馈机制。下游处理不过来时，能告诉上游「慢一点 / 少推一点」，避免数据把内存或线程冲爆。内部相关代码（写在Sinks管道上）：

```java
Sinks.many().replay().limit(1024) + tryEmitNext
```

本质是带上限的缓冲区，不是严格意义的强背压，超过1024条消息将抛弃，写的时候也是一股脑往管道塞，不会实时根据下游减慢速度。

**订阅者**

最外层订阅者是「把 `Flux<String>` 写成 HTTP 响应」的那一层（Spring 在返回 `Flux` 时帮你订上），再往外是浏览器在读响应体（`fetch` / `ReadableStream` 一行行拉 NDJSON）。

## 注意事项

消息在会话内是总体有序的，依靠发布者推送消息时先来后到保证有序，类似于简单队列，没有其他兜底机制，这意味着会话内若出现多线程场景，可能会导致乱序。尽管每次推送的消息都携带`seq`标号，但仅仅是个顺序标识，实际没利用到。

# 为什么选择`Project Reactor`？

### 主聊天在干什么？
用户发一句 → 后端编排、出步骤、吐正文、可能再跑质量环 → **中间过程要立刻出现在界面上**，不能等全部算完再一次性返回。

这天然是一条**长时间、多段事件流**，不是普通「请求 → 一个 JSON → 结束」。

### 为啥 Reactor 合适（通俗版）？
1. **天生表达「流」**  
   `Flux` 就是「陆续往外冒东西」：一行行 NDJSON（`route` / `step` / `text_delta`）。用回调也能做，但多步串起来容易乱成意大利面。
2. **和 Spring 一条绳上的蚂蚱**  
   你们是 Spring Boot + Spring AI。返回 `Flux`、在管道里 `flatMap` / `doFinally`，是生态里的常规写法，文档和例子都多，不必另起一套异步框架。
4. **取消、收尾有现成钩子**  
   用户断开、出错、正常结束，可以在 `doFinally` 里清工作区、决定写不写 Memory——流式聊天很需要这种「收场逻辑」。

### 为啥不（一定）用别的？
| 方案                  | 也能做流式吗             | 相对你们的代价                                   |
| --------------------- | ------------------------ | ------------------------------------------------ |
| 纯同步 Servlet 阻塞写 | 能，但线程易被长时间占满 | 编排+模型很慢，线程模型更吃力                    |
| 自己回调 / 线程池拼   | 能                       | 组合、取消、错误传递更碎                         |
| WebSocket 自建协议    | 能                       | 前端、网关、重连都要另设计；你们已用 HTTP NDJSON |
| RxJava 等             | 类似模型                 | 不如 Reactor 契合Spring生态                      |
