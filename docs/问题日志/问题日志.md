# [2026/4/6] 添加less相关依赖

根据你的 `package.json`，需要添加 Less 相关的依赖。Vite 原生支持 Less，只需要安装 Less 本身即可。

## 正确添加 Less 依赖

**步骤1：安装 Less**

在项目根目录执行：

```bash
npm install -D less
```

**注意**：

- 使用 `-D` (或 `--save-dev`) 因为 Less 是开发依赖
- **不需要**安装 `less-loader`（那是 Webpack 需要的）
- Vite 会自动处理 Less 文件的编译

**步骤2：验证安装**

安装成功后，`package.json` 的 `devDependencies` 中会新增：

```json
"devDependencies": {
  "@types/node": "^24.12.2",
  "@vitejs/plugin-vue": "^6.0.5",
  "@vue/tsconfig": "^0.9.1",
  "less": "^4.4.2",        // 新增
  "typescript": "~6.0.2",
  "vite": "^8.0.4",
  "vue-tsc": "^3.2.6"
}
```

**步骤3：在 Vue 组件中使用 Less**

**在 `<style>` 标签中指定 `lang="less"`：**

```vue
<template>
  <div class="container">
    <h1>Hello Less</h1>
    <button class="btn">按钮</button>
  </div>
</template>

<style scoped lang="less">
// 定义变量
@primary-color: #42b983;
@padding: 20px;

.container {
  padding: @padding;
  
  h1 {
    color: @primary-color;
  }
  
  // 嵌套语法
  .btn {
    background-color: @primary-color;
    color: white;
    padding: 10px 20px;
    
    &:hover {
      background-color: darken(@primary-color, 10%);
    }
  }
}
</style>
```

**步骤4：也可以导入外部 Less 文件**

**创建 `src/styles/variables.less`：**

```less
// 全局变量
@primary-color: #42b983;
@danger-color: #ff4444;
@font-size-base: 14px;
```

**在组件中导入：**

```vue
<style scoped lang="less">
@import '@/styles/variables.less';

.container {
  color: @primary-color;
  font-size: @font-size-base;
}
</style>
```

**可选：配置全局 Less 变量（无需在每个文件导入）**

如果需要全局使用变量，可以在 `vite.config.ts` 中配置：

```typescript
import { defineConfig } from 'vite'
import vue from '@vitejs/plugin-vue'
import path from 'path'

export default defineConfig({
  plugins: [vue()],
  css: {
    preprocessorOptions: {
      less: {
        additionalData: `@import "@/styles/variables.less";` // 全局注入
      }
    }
  },
  resolve: {
    alias: {
      '@': path.resolve(__dirname, './src')
    }
  }
})
```

配置后，组件中无需手动 `@import` 即可使用全局变量：

```vue
<style scoped lang="less">
.btn {
  color: @primary-color; // 直接使用，无需导入
}
</style>
```

## 常见问题

**问题1：安装 Less 后报错**

```bash
# 如果安装失败，尝试清除缓存重新安装
npm cache clean --force
rm -rf node_modules package-lock.json
npm install
npm install -D less
```

**问题2：TypeScript 类型提示**

Less 不需要额外的类型声明，Vite 会处理。如果需要导入 `.less` 文件的类型，可以创建 `src/vite-env.d.ts`（如果不存在）：

```typescript
/// <reference types="vite/client" />

declare module '*.less' {
  const content: { [className: string]: string }
  export default content
}
```

**问题3：想用 Less 的高级功能**

Less 支持的所有功能都可以直接使用：

```less
// 混入（Mixins）
.border-radius(@radius) {
  border-radius: @radius;
}

// 函数
@base: #f04615;
@bg: @base + #333;

// 作用域
@var: red;
.page {
  @var: blue;
  color: @var; // blue
}
```

2. 在任意 `.vue` 组件中添加带 Less 样式的代码

**总结：只需执行 `npm install -D less` 一条命令即可！** Vite 的零配置特性让你不需要像 Webpack 那样配置 loader。

# [2026/4/6] 配置路由

根据你的 `package.json`，需要安装 Vue Router 并进行配置。以下是完整步骤：

**步骤1：安装 Vue Router**

在项目根目录执行：

```bash
npm install vue-router@4
```

**注意**：Vue 3 对应 Vue Router 4.x 版本

安装成功后，`package.json` 的 `dependencies` 会新增：

**步骤2：创建路由配置文件**

创建 `src/router/index.ts`

```typescript
import { createRouter, createWebHistory } from 'vue-router'
import type { RouteRecordRaw } from 'vue-router'

// 定义路由配置
const routes: RouteRecordRaw[] = [
  {
    path: '/',
    name: 'home',
    component: () => import('@/views/HomeView.vue')  // 懒加载
  },
  {
    path: '/about',
    name: 'about',
    component: () => import('@/views/AboutView.vue')
  },
  {
    path: '/chat',
    name: 'chat',
    component: () => import('@/views/ChatView.vue')
  }
]

// 创建路由实例
const router = createRouter({
  history: createWebHistory(import.meta.env.BASE_URL),  // HTML5 模式
  routes
})

// 可选：全局路由守卫
router.beforeEach((to, from, next) => {
  console.log('导航到:', to.path)
  next()
})

export default router
```

这是一个典型的 **Spring AI 版本间 artifactId 变更** 问题。

## 2.1 🔍 问题根源分析

通过对比您本地 Maven 仓库中的 BOM 文件，我发现了关键差异：

| Spring AI 版本      | OpenAI Starter 的 artifactId           |
| ------------------- | -------------------------------------- |
| **1.0.0-M6**        | `spring-ai-openai-spring-boot-starter` |
| **1.0.0（正式版）** | `spring-ai-starter-model-openai`       |
| **1.1.2**           | `spring-ai-starter-model-openai`       |

**问题原因**：
您的 `pom.xml` 中使用了旧的 artifactId `spring-ai-openai-spring-boot-starter`，但 Spring AI 1.0.0+ 的 BOM 中只定义了新的 artifactId `spring-ai-starter-model-openai`，导致 Maven 无法找到版本号，从而触发依赖解析失败和本地仓库清理。

## 2.6 🎯 为什么只有 1.0.0-M6 能工作？

因为您一直使用 `spring-ai-openai-spring-boot-starter` 这个 artifactId，而这个 artifactId 只在 1.0.0-M6 的 BOM 中存在。Spring AI 团队在正式版中统一了命名规范，将 `-spring-boot-starter` 后缀移到了中间位置。

现在您已经了解了问题的根本原因，应该可以自由选择任何兼容的 Spring AI 版本了！

## 原因分析

核心错误是：

Property 'sqlSessionFactory' or 'sqlSessionTemplate' are required

这说明 `SpringAiChatMemoryMapper` 被注册了，但 MyBatis 的 `SqlSessionFactory` 从未创建。

你的技术栈是 Spring Boot 4.1.0，但 `pom.xml` 里用的是：

mybatis-plus-spring-boot3-starter  (3.5.14)

`mybatis-plus-spring-boot3-starter` 的自动配置面向 Spring Boot 3，在 Spring Boot 4 下 不会生效，因此不会创建 `SqlSessionFactory`。

同时 `@MapperScan("com.mychat.mapper")` 仍会扫描并注册 Mapper，Mapper 初始化时找不到 `sqlSessionFactory`，就会报你看到的错误。

数据源（HikariCP）能连上 MySQL，说明问题不在 `application.yaml` 的数据库配置，而在 MyBatis-Plus Starter 与 Spring Boot 版本不匹配。

## 解决方案（Cursor Composer 2.5）

Spring Boot 4 应使用 `mybatis-plus-spring-boot4-starter`，建议 3.5.15+。

我已在你的 `pom.xml` 中做了修改：

1. `mybatis-plus.version`：`3.5.14` → `3.5.15`
2. `mybatis-plus-spring-boot3-starter` → `mybatis-plus-spring-boot4-starter`

本地编译已通过，原来的 `sqlSessionFactory` 错误已消失。

根本原因是 PostgreSQL 数据库中**未安装 pgvector 扩展**。

日志中的关键证据：

```
CREATE EXTENSION IF NOT EXISTS vector;
```

安装教程：https://juejin.cn/post/7636343113468772386

教程2：[PostgreSQL 向量扩展插件pgvector安装-CSDN博客](https://blog.csdn.net/m0_74834369/article/details/155921982)

教程3要你自己下载扩展源码手动编译。

一个可用的预编译包下载：https://github.com/andreiramani/pgvector_pgsql_windows/releases

下载完后在PGAdmin4的query tool输入`CREATE EXTENSION IF NOT EXISTS vector;`，若返回查询结果则成功。

> 之后上传同一个文件又报错

错误变了：现在 `vector` 类型已被识别，但 `public.vector_store` 表本身不存在了。

之前第一次启动时 Spring AI 检测到表已存在所以跳过了建表：

```
Skipping the schema initialization for the table: public.vector_store
```

现在表消失了（可能在 pgvector 安装过程中被清掉了），而 Spring AI 的 `vectorTableValidationsEnabled: false` 让它不会主动重建表。

**修复方法**：在 pgAdmin 的 Query Tool 中手动创建表：

```
CREATE EXTENSION IF NOT EXISTS vector;
CREATE EXTENSION IF NOT EXISTS "uuid-ossp";

CREATE TABLE IF NOT EXISTS public.vector_store (
    id uuid DEFAULT uuid_generate_v4() PRIMARY KEY,
    content text,
    metadata jsonb,
    embedding vector(1536)
);

CREATE INDEX IF NOT EXISTS idx_vector_store_embedding
    ON public.vector_store
    USING hnsw (embedding vector_cosine_ops);
```

然后**重启后端服务**即可正常上传。

> 这张表看起来和普通的关系型表好像没什么区别？

确实，它的基本结构就是一个普通的 PostgreSQL 表。唯一让它"特殊"的是两点：

1. **`embedding vector(1536)` 列** — 这是 pgvector 扩展提供的向量数据类型，支持 `<=>`（余弦距离）、`<#>`（内积）等向量相似度运算符
2. **HNSW 索引** — `USING hnsw (embedding vector_cosine_ops)`，专门针对向量列的近似最近邻搜索索引，实现高效的语义相似度检索

其余列（`id`、`content`、`metadata jsonb`）都是标准的关系型字段。本质上 pgvector 就是把向量当作一种特殊列类型嵌入到普通 SQL 表中，用 SQL 就能做语义搜索，而不是引入一个独立的外部向量数据库。

有一轮修改方案值得注意：

> ## 根因确认
>
> 从日志可以确认：`toolChatClient` 的 `defaultSystem` 中的 `WorkspaceContext.get()` 始终返回 `null`，导致 AI 收到的永远是通用提示（"路径都是相对于默认工作区的相对路径"），而非包含具体工作目录的提示。
>
> Spring AI 评估 `defaultSystem(Consumer<PromptSystemSpec>)` 的时机不确定——有时是在请求线程上（此时 `WorkspaceContext` 已设），有时是在 Reactor 调度链中（此时 ThreadLocal 丢失或未设）。这是你系统提示中永远看不到 "当前工作目录: personal-blog" 这类信息的根因。
>
> ## 修复方案
>
> ### 改动 1：`AiConfiguration.java` — 移除 `toolChatClient` 中依赖 `WorkspaceContext` 的动态提示
>
> 将 workspace 相关的逻辑从 `defaultSystem` 中彻底移除，`defaultSystem` 只保留纯静态的通用提示：
>
> ```java
> // toolChatClient 的 defaultSystem 改为：
> .defaultSystem("""
>     所有涉及文件的查看、创建、写入、修改、删除、重命名、复制操作，都必须通过可用工具实际执行。
>     你绝不能在回复中假装已经完成了文件操作。
>     路径都是相对于当前工作目录的**相对路径**。
>     """)
> ```
>
> `ragChatClient` 的 `defaultSystem` 是纯静态字符串，**不受此 bug 影响**，无需改动。
>
> ### 改动 2：`ChatController.java` — 在请求体中注入 workspace 感知的系统提示

>
> ```

>   ToolCall[name=write, arguments={path: "src/data/articles.js", ...}],

> MethodToolCallback: Successful execution ✅

>
> 模型生成的 `toolCalls[]` 非空，Spring AI 正常执行。
>
> ## 第二轮（失败）
>
> ```
> AssistantMessage [toolCalls=[]],
> textContent="好的，我来优化第3点...先看一下当前的路由配置..."
> ```
>
> 模型生成的 `toolCalls[]` 为**空**，直接输出纯文本。它只是在**描述计划**，没有实际发起任何工具调用。
>
> ## 根因
>
> deepseek-v4-flash 在**多轮对话的工具调用**中存在**工具调用疲劳**：
>
> 1. **首轮工作正常**：新会话上下文干净，模型积极使用工具
> 2. **从第二轮开始**：上下文堆积了大量工具结果（文章数据写入结果等），系统提示的位置被推后，模型**从"做"退化为"说"**——它认为描述方案就够了，不再生成新工具调用
>
> 这不是 FileTools、WorkspaceContext 或系统提示注入的问题（你的修复已生效）。这是**模型自身不稳定的工具调用倾向**。
>
> ## 可行的缓解方案
>
> 按投入产出比排序：
>
> | 方案                                                         | 改动量                    | 效果                  |
> | ------------------------------------------------------------ | ------------------------- | --------------------- |
> | **① 每条用户消息尾部追加指令**：`"请直接使用工具执行操作，不要只描述计划"` | 前端 1 行                 | 中等                  |
> | **② 系统提示中增加强制工具调用约束**：加入"如果你不实际调用工具就失败"的表述 | 后端 1 处                 | 中等                  |

> | **④ `tool_choice: "required"`**（如果 DeepSeek 支持）强制每轮必须调工具 | `application.yaml` 1 行   | 大（需验证 API 支持） |
> | **⑤ 切换更强模型**：deepseek-v4-flash → deepseek-v4-pro 或 GPT-4 | `application.yaml` 1 行   | 最大                  |
>

实际上，单纯换用更强的模型（deepseek-v4-flash --> deepseek-v4-pro）并不能解决问题，要每次对话完手动强调：“请直接使用工具执行操作，不要只描述计划！”才算真正解决了问题。相关分析：

> 换用deepseek-v4-pro后，AI第二次起增删改失效的问题依旧存在，唯一有效的手段是每轮对话后补充一句：“请直接使用工具执行操作，不要只描述计划”。这在网络上有没有类似的问题？
> 我看见大部分AI编程工具比如cursor都会区分不同模式，比如debug模式、plan模式（只读）、build模式（可以直接修改项目），这是否和我们存在的问题有关？

## 1. 这是否是已知问题？

是的，这是一个被充分记录的 LLM 行为模式，通常称为：

- **"Tool calling fatigue"** 或 **"Tool neglect"** — 随着对话上下文增长（尤其是大量工具调用结果的堆积），模型倾向于停止生成工具调用，转为纯文本描述。
- **"Lazy tool use"** — 模型认为"描述计划"比"实际执行"更省 token。
- Anthropic 的 [Tool Use 文档](https://docs.anthropic.com/en/docs/build-with-claude/tool-use) 和 OpenAI 的 [Function Calling 指南](https://platform.openai.com/docs/guides/function-calling) 都提到了这种不稳定性：**越是复杂、上下文越长，模型越容易跳过工具调用**。
- 社区中有大量相关讨论，例如 Reddit 的 r/ClaudeAI 和 GitHub issues 中关于 "model stops calling tools after several rounds" 的报告。

**这本质上是模型行为缺陷，而非代码逻辑 bug。** 你的"每轮追加提示"的解法是业界常规缓解手段之一。

## 2. 你的直觉完全正确 — 这就是模式的概念

Cursor/Windsurf 等工具的 **Plan 模式和 Build 模式** 与你的问题直接相关：

| 模式             | 行为                                | 工具可用性 |
| ---------------- | ----------------------------------- | ---------- |
| **Plan（只读）** | AI 只分析、描述计划，不修改任何文件 | ❌ 无写工具 |
| **Build**        | AI 必须通过工具实际执行操作         | ✅ 所有工具 |
| **Debug**        | AI 以诊断为重点                     | 有限工具   |

**模式的核心价值正是在于给模型明确的"身份信号"**：当模型知道自己在 Plan 模式时，它应该"说"；当在 Build 模式时，它必须"做"。这消除了模型的角色模糊——你的 AI 经常"只说不做"，就是因为它在同一会话中既有分析（plan）又有执行（build）双重目标，模型不确定何时该切换。

### 对你的项目的建议

在 `ChatController.java` 中引入模式切换：

```java
public enum ChatMode {
    PLAN,    // 系统提示：只分析，不要调用任何写工具
    BUILD    // 系统提示：必须通过工具执行，不能只描述
}
```

- 前端发送消息时携带 `mode` 参数（默认 BUILD）
- 在 `buildWorkspaceSystemPrompt()` 中根据模式注入不同指令
- 甚至可以动态禁用写工具（通过 `ToolCallback` 过滤）

这是最根本的解决方案：**不给模型"说出来就算做完"的选择权**。

# [11-2026-8-9] 主聊天合并 Agent 后「联网工具不可用」

背景：P2-10 将 Orchestrator / Evaluator-Optimizer 等能力并入主聊天（默认 `orchestrate` + `qualityLoop`）后，前端时间线里 search Worker 常报联网失败，用户侧感觉像「Agent 合并把搜索弄坏了」。对照旧后端 `my-chat-server-old`：当时只靠 Smithery MCP，进程里也没有 `EXA_API_KEY`，搜索却能用。

## 现象

- 主聊天需要实时资讯时，模型走 MCP `execute` → Exa，最终仍答不出可用网页结果。
- 控制台 / Postman 可见 `ToolExecutionException`、Worker 收尾异常，或模型自称「联网工具不可用」。
- 编排层本身（`retrieve_kb` → `search` → `finish`）往往是成功的——失败集中在 **search Worker 的外部搜索依赖**。

## DEBUG 假设与结论（按排查顺序）

| 假设 | 结论 | 关键证据 |
|------|------|----------|
| A. 合并后 MCP 未挂到 ChatClient | **否定** | 实际执行了 `get_toolbox_status` / `search_toolbox` / `execute` |
| B. 模型误用连接名 `connections.search` | **成立（次因）** | `Connection not found: search`（工具箱里是 **exa**） |
| C. Smithery 分发到 `mcp.exa.ai` 被 Cloudflare 拦截 | **成立（外部主因）** | `Unable to access mcp.exa.ai` + HTTP **403** |
| D. 工具异常打断 Worker `.call()` | **成立** | 栈落到 `workerSearch` → `.content()` |
| E. 默认 Orchestrator 让 search 更常出现 | **成立（暴露面）** | 主路常 `retrieve_kb` 再 `search`；旧主聊天未必每次搜网 |
| F. 本地 `searchWeb` Jackson 组 JSON NPE | **成立（自造 bug）** | `ObjectNode.put(String, JsonNode) ... is null`，请求未发出 |
| G. `EXA_API_KEY` 填错（误用 Smithery key） | **成立** | Exa REST **401 Invalid API key** |
| H. DuckDuckGo 国内兜底不可达 | **成立** | `HTTP connect timed out` |

一句话：**合并没有拆掉 MCP**；默认多步编排把本就脆弱的 Smithery→Exa 链路用得更勤，叠加模型用错连接名、工具异常硬抛、以及后来自建 REST 的 NPE / 密钥混淆，才表现为「联网不可用」。

## 排查历程（简表）

1. **对照日志**：MCP 工具能调通，但 `connections.search` 不存在；改用 `connections.exa` 后仍卡在 Cloudflare **403**。
2. **第一轮缓解**：抽出 `SearchSystemPrompts`（禁止臆造 `connections.search`）；`ToolExecutionExceptionProcessor(alwaysThrow=false)`，失败回灌模型，避免整段 Worker 崩掉。结果：连接名错误消失，Worker 能收尾，**403 仍在**。
3. **第二轮**：新增本地工具 `WebSearchTools.searchWeb`，提示改为**优先 searchWeb**，意图绕开 `mcp.exa.ai`。
4. **配了 `EXA_API_KEY` 仍失败**：埋点显示 `hasExaKey=true` 却 NPE——Jackson `put(String, JsonNode)` 返回旧值（null），链式 `.toString()` 炸掉，**REST 根本没发出去**。改为 `ObjectNode#set` + `writeValueAsString`。
5. **NPE 修好后**：Exa REST 返回 **401**——环境里的「EXA」密钥实际常是 `SMITHERY_API_KEY` 或非 Dashboard 密钥；DuckDuckGo 短超时又连不上。补齐 Bocha / Tavily 回退与错误文案。
6. **验证通过**：真正的 Exa Dashboard key 注入并重启后，`searchWeb` → `provider=exa-rest`、`status=200`，Orchestrator search Worker 能汇总实时结果（如行情类问题）。调试埋点（`AgentDebugLog` 等）随后清理。

## 最终方案（保留代码）

| 项 | 说明 |
|----|------|
| `SearchSystemPrompts` | 优先 `searchWeb`；MCP 仅备选；连接名必须是 **exa** |
| `WebSearchTools.searchWeb` | **Exa REST → Bocha → Tavily → DuckDuckGo（短超时）**，不经 `mcp.exa.ai` |
| `AiConfiguration` | 注册 `WebSearchTools`；`ToolExecutionExceptionProcessor(alwaysThrow=false)` |
| `application.yaml` | `app.search.exa/bocha/tavily.api-key` ← 环境变量 |
| 文档 | P2-10 v1.1 §2.2.2 写明外部局限与密钥易错点 |

**密钥对照（已踩坑）**：

| 环境变量 | 用途 | 常见错误 |
|----------|------|----------|
| `EXA_API_KEY` | 直连 `https://api.exa.ai/search` | 误填 `SMITHERY_API_KEY` → 401 |
| `SMITHERY_API_KEY` | MCP `mcp.smithery.run` Bearer | 不能当 Exa REST key；且下游 `mcp.exa.ai` 可能 403 |
| `BOCHA_API_KEY` / `TAVILY_API_KEY` | 备用搜索 | 可选；国内建议至少配一个 |

## 为何旧代码没有 `EXA_API_KEY` 也能搜？

旧后端（`my-chat-server-old`）**根本没有** `WebSearchTools` / `app.search.exa`：

- 联网只走 **Smithery 代理**：本机 → `mcp.smithery.run`（`SMITHERY_API_KEY`）→ 工具箱里的 Exa。
- Exa 凭据在 **Smithery / 工具箱侧** 管理，进程不直连 `api.exa.ai`，因此不需要本地 `EXA_API_KEY`。
- 旧主聊天也不默认 Orchestrator，search MCP 调用更少，Smithery→Exa 偶发故障更不易被感知。

新代码默认优先本机直连，是因为调试时 **代理链路已被 Cloudflare 403 证伪**，不是产品上主动弃用 Smithery。MCP（天气等）与 `SMITHERY_API_KEY` 配置仍保留；搜网若代理恢复稳定，仍可再抬优先级。

## 后人排查顺序

1. 看是否调用了 `searchWeb`，而不是反复死磕 `connections.exa` 的 403。
2. 若返回含 `401 Invalid API key`：到 [Exa Dashboard](https://dashboard.exa.ai/api-keys) 换真正密钥，注入进程环境变量后**重启**（IDE 里改 env 不重启无效）。
3. 无 Exa 时配 `BOCHA_API_KEY` 或 `TAVILY_API_KEY`；不要指望国内 DuckDuckGo 稳定。
4. MCP Cloudflare 403 属上游，**改 Orchestrator / Routing 解决不了**。

# [12-2026-8-9] 编排最终答复只剩提纲，干货藏在时间线

## 现象

多步 Orchestrator（如「知识库答 Java 三大特性 + 联网实践案例」）后：主气泡 / `spring_ai_chat_memory` 只有一句「结合…向用户完整作答：首先给出…」；完整定义与案例代码在 `chat_assistant_turns.parts` 的 step observation 里，需手动展开时间线。
